# Parallel file transfers

The executor admits eligible independent file transfers through a bounded FIFO queue. When one job finishes, the next eligible job can start without waiting for all other transfers. Only ready items with one upload or download and optional baseline establishment may overlap. Moves, merges, deletions and remote-verification steps are barriers. Admission compares entry IDs, remote file IDs, all recorded and planned paths, case-folded NFC aliases and ancestor relationships. Jobs never overtake a waiting predecessor, and reported results retain plan order.

Each worker retains the existing transfer preconditions, isolated staging and recovery mechanisms. A failure prevents further jobs from starting and the executor waits for all started workers. Baseline object writes are serialized; durable state is published once, only after queue processing finishes and the plan anchor is checked under the durable-state mutex. If a job fails, the entries whose steps all completed and were verified are still published (under the same anchor check) so that a later local edit is not mistaken for an unrelated concurrent creation; the failed entry is never recorded. Physical operations can have completed even when publication fails; subsequent inventory/recovery must reconcile them, just as with the serial executor.

Transfer journal reads and mutations are serialized per adapter and runtime scope, including across journal-store instances in the same JavaScript context. Before transfers start, an already-running local inventory is drained so its file reads do not overlap the transfers. The existing runtime writer lease remains responsible for coordination across supported application contexts.

Advanced settings expose worker count and an estimated concurrent memory budget. The default of one worker preserves serial behavior; the device's existing in-flight read budget caps the configured value. The estimate reserves four times the largest observed file size plus up to one configured chunk per job. An individually oversized estimate runs alone; this is admission control, not a hard limit on process memory or adapter allocations. Chunk size may be enlarged for Nextcloud geometry, making actual allocation differ from the estimate. Mobile background execution, adapter atomicity, and power-loss durability are not guaranteed by these limits.

Parallel transfers remain opt-in (default: one worker). The whole live suite (`npm run e2e:live` with `NYRA_E2E_TRANSFER_CONCURRENCY=4`, 25 scenarios) and a live benchmark (`npm run bench:live`) passed against one real Nextcloud server on 2026-11-02; no phone and no second server type was tested. Do not assume the Galaxy A52 manifest failure has been fixed without reproducing it. WebDAV folder removal uses a conditional collection ETag but remains subject to a list/delete race on servers that do not propagate child changes or enforce the precondition. No actual Android or Nextcloud server performance claim is made from in-memory tests. Sync is not a replacement for an independent, tested backup.

Offline benchmarks (`npx vitest run tests/executor-performance.test.ts --disableConsoleIntercept`, 2026-11-02, WSL2 on a Windows-mounted drive; this host's timers are coarse, so absolute numbers are inflated and vary by load): (1) mock adapters, 24 tiny uploads, 30 ms artificial delay each: 1 worker 815 ms, 2 workers 404 ms, 4 workers 232 ms, 8 workers 119 ms; (2) the real local/remote mutators against the in-memory DAV server with a nominal 8 ms delay per HTTP request, 12 small and 4 chunked uploads: 1 worker 2822 ms, 2 workers 1515 ms, 4 workers 922 ms. Parallel runs issue a few extra requests (178 vs 188), all from lost `MKCOL` directory-creation races that are answered with 405 and tolerated. These measure scheduling and the request sequence only, not network throughput, memory use, Android performance, or a real Nextcloud installation.

Live benchmark (`npm run bench:live`, one run per setting, 40 files / 5.9 MiB in six folders incl. four 1.5 MiB files, content verified by SHA-256, desktop-class devices on this machine and network, 2026-11-02): 1 worker upload 20.7 s / download 6.7 s; 2 workers 14.1 s / 4.5 s; 4 workers 10.8 s / 3.0 s; 8 workers 9.5 s / 2.5 s. Single runs, so expect run-to-run variation.

Server behaviour found live: concurrent creation of the same new folder is answered with HTTP 423 (not 405), so folder creation inside one mutator is serialized and a 423 (refused before anything ran) is repeated for writes too; before this, such 423s aborted whole sync cycles.

Offline restart tests use actual local and remote mutators with an in-memory DAV server. They cover one successful upload alongside a failed upload, re-inventory and convergence after reopening state, as well as two overlapping chunked uploads where one is interrupted after its first chunk and resumes from its journal after restart. These are fault simulations, not operating-system crash or physical-device tests.
